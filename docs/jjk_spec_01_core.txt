# JJK 서버 명세 — 01. 핵심 규칙·빌드·전투·CE

> 대상: Minecraft Fabric 1.21.1 서버 모드
> 원칙: 확정 수치는 임의 변경 금지. 명백한 계산 오류와 런타임/빌드 오류만 수정.
> \*\*틱 기준: 1초 = 20틱 (1틱 = 50ms). 모든 tick 환산은 이 기준을 따른다.\*\*
> \*\*CD 단위: 틱(ticks). 스킬 표의 CD=4는 4틱=0.2초.\*\*

\---

## §0. CLAUDE.md 작업 규칙

1. 기존 확정 수치와 밸런스 값은 임의 변경하지 않는다.
2. 중복 내용은 최신·상세한 쪽만 남긴다.
3. Java 코드 블록에는 실제 컴파일 가능한 Java 예시만 둔다.
4. `\[AI-ADD]` / `\[DOCX]` / `\[AI-FIX]` / `\[AI-FINAL]` 태그는 문서 주석 전용. Java 코드 블록 안에 포함 금지(주석 형태도 금지).
5. Mixin 추가 시 `jjk.mixins.json`도 동시에 수정한다.
6. PlayerData 필드 추가 시 `snapshot()` 복사와 DB 마이그레이션을 함께 작성한다.
7. `bindingVowDeclaredTick`은 `CooldownManager`가 아닌 `PlayerData`에 저장. 미선언 상태 sentinel = `-1L`.
8. 각성 발동 전 `awakeningCooldownUntil` 체크 필수. 중복 발동 방지.
9. `DomainInstance`는 class(record 아님). `wallHp`·`currentRadius`는 가변 필드.
10. 스킬 표의 CD와 §13-3 cooldown\_persist는 같은 키를 공유한다. 스킬 keyId와 쿨타임 cooldown\_type을 혼동하지 말 것.

### 1-5. 서버 권위 원칙

클라이언트는 키 입력과 표시만 담당한다. 데미지, CE 소모, 쿨타임, 영역 충돌, 손가락 드롭, 캐릭터 선택 중복 검사는 모두 서버에서 확정한다.

### 1-6. Mixin 후킹 명세

`ServerPlayerEntityMixin`

&#x20;   @Inject method="tick" at=TAIL
      → CEManager.regenTick(player)
      → AwakeningManager.tickCheck(data, currentTick)   ← tick 기반 만료 체크
      → ZoneStateManager.tick(player)
      → BurdenManager.tick(player)

    @Inject method="onDeath" at=HEAD
      → PlayerRepository.saveImmediate(data)            ← 저장 주체는 PlayerRepository
      → AwakeningManager.reset(player)
      → ZoneStateManager.reset(player)


`LivingEntityMixin`

&#x20;   @Inject method="damage" at=HEAD cancellable=true
      → InfinityHandler.checkAndCancel(self, source, cir)
      → TickDamageCap 초과 시 cir.setReturnValue(false)

    @ModifyVariable method="damage" ordinal=0 at=HEAD
      → isSoulDirect=true 시 effectiveDefense=0 강제
      → NON\_SORCERER defense 배율 적용


`ServerWorldMixin`

&#x20;   @Inject method="tick" at=TAIL
      → DomainManager.tickDomains(world)


주의: `@Inject cancellable=true` 남용 금지. Mixin 추가 시 `jjk.mixins.json` 동시 등록 필수.

## §2. 서버 성능과 운영 기준

### 2-1. 목표 환경

Fabric 1.21.1, Java 21, dedicated server 기준. 클라이언트 전용 렌더링 코드는 `client` 소스셋 또는 `EnvType.CLIENT` 분기로 격리한다.

### 2-2. Tick 예산

서버 메인 루프는 평균 50ms/tick(= 20TPS) 이하를 유지한다. 영역, 장막, 광역 스킬은 엔티티 검색 범위를 캐시하고 5틱 단위 배치 처리 가능.

### 2-3. 네트워크 원칙

스킬 결과 패킷은 연출용이다. 클라이언트가 보낸 데미지·명중·쿨타임 결과는 신뢰하지 않는다.

### 2-4. 저장 원칙

손가락 획득, 캐릭터 선택, 사망, 처형검 획득, 영역 전개 시작/종료는 즉시 저장 대상이다. 일반 CE·HP 변화는 주기 저장 가능.

### 2-5. 성능 모니터링

|지표|경고|위험|조치|
|-|-|-|-|
|TPS|18 미만|15 미만|광역 tick 주기 증가, particle 감축|
|메인스레드|45ms/tick 초과|60ms/tick 초과|영역 엔티티 스캔 분산|
|힙|75% 초과|90% 초과|캐시 TTL 축소|
|패킷|120/s/player 초과|200/s/player 초과|S2C 연출 패킷 병합|
|엔티티|800 초과|1200 초과|식신·투사체 lifetime 점검|

## §3. 전투 핵심 시스템

### 3-1. 속박(Binding Vow)

선언 후 15초(300틱) 내 조건 미달성 시 자동 해제한다. `bindingVowDeclaredTick`은 `PlayerData`에 저장한다. 미선언 상태 = `-1L`. 속박 파훼 조건은 특급 이상 스킬 직격 시 해제.

### 3-2. 흑섬(Black Flash)

|항목|값|
|-|-|
|판정|공격 전후 Just Frame 윈도우(8\~12틱) 내|
|기본 확률|Zone 없을 때 `config.blackFlashBaseRate`%, Zone 중 +`config.blackFlashZoneBonus`%|
|데미지|base × 2.5|
|후속 효과|Zone 진입, 콤보 보정|

⚠️ 원작 vs 게임화 결정:
원작(Akutami Vol.6): 흑섬 데미지 = base^2.5(지수승)
이 서버: base × 2.5(배율). 이유: base^2.5는 TickDamageCap에 걸려 실질 효과 없음.
이 결정은 확정값. 코드에서 임의 변경 금지.

### 3-3. Zone

흑섬 성공 또는 특정 콤보 조건 달성 시 진입한다. 종료 후 `zonePenaltyUntilTick`까지 최종 배율 ×0.5 페널티를 적용한다. Zone 관리는 `ZoneStateManager`가 담당하고, `ComboTracker`와 흑섬 판정이 같은 Just Frame 윈도우(8\~12틱)를 공유한다.

### 3-4. TickDamageCap

PvP 최종 피해 상한은 `max\_hp × 0.40`이다. PvE 상한은 config로 분리 가능하지만 기본 전투 공식 순서는 동일하다.

### 3-5. Just Frame

Just Frame 윈도우는 8\~12틱이다. 30틱 동안 후속 입력이 없으면 콤보를 리셋한다. 이 윈도우는 흑섬 판정과 콤보 시스템이 공유한다.

### 3-6. CombatPipeline 순서

`CombatPipeline.process(PlayerData attacker, PlayerData target, SkillUseC2SPacket packet, long currentTick)` 를 다음 순서로 실행한다:

1. **입력 검증** — TeamManager: 같은 진영 여부, characterId 소유 여부
2. **CE·쿨타임 검증** — CEManager: ceCurrent 충분 여부, cooldowns Map 만료 여부
3. **명중·거리·시야 검증** — 서버 측 거리/시야 계산
4. **baseDamage 산출** — techniques.json 기반
5. **흑섬·Zone·각성 판정** — 이 단계에서 `AwakeningManager.checkAndActivate(data, hpCurrent, hpMax, tick)` 호출
6. **방어·저항·무하한·영혼 데미지 처리** — InfinityHandler, isSoulDirect, NON\_SORCERER 배율
7. **최종 배율 clamp** — ×0.25\~×4.0
8. **TickDamageCap 적용** — `min(finalDamage, target.hpMax \* 0.40f)`
9. **데미지 반영 및 S2C 전송** — SkillResultS2CPacket

### 3-7. 각성(覚醒) 시스템

발동 조건: `currentHp ≤ maxHp × 0.30`
발동 위치: CombatPipeline 5단계. `AwakeningManager.checkAndActivate(data, currentHp, maxHp, tick)` 호출.
지속시간: 8초(160틱) — `awakeningEndTick = currentTick + 160`
쿨타임: 120초(2400틱) — `awakeningCooldownUntil = currentTick + 2400`
효과: `finalMultiplier × 1.25`(클램프 ×4.0 내 포함)
해제: `awakeningEndTick` 도달 시 `tickCheck`에서 자동 해제

`AwakeningManager` 구현:

&#x20;   checkAndActivate(PlayerData data, float currentHp, float maxHp, long tick):
      if (currentHp > maxHp \* 0.30f) return;
      if (tick < data.awakeningCooldownUntil) return;
      if (data.awakeningActive) return;
      data.awakeningActive = true;
      data.awakeningEndTick = tick + 160;
      data.awakeningCooldownUntil = tick + 2400;
      AwakeningS2CPacket(playerUuid, true) 전송

    tickCheck(PlayerData data, long tick):
      if (data.awakeningActive \&\& tick >= data.awakeningEndTick)
        data.awakeningActive = false;
        AwakeningS2CPacket(playerUuid, false) 전송


주의: `awakeningCooldownUntil` 체크 필수. `checkAndActivate`는 CombatPipeline에서만 호출한다. `tickCheck`는 Mixin tick at=TAIL에서 호출한다. 두 경로가 분리되어 있어 중복 발동은 `awakeningActive` 플래그가 막는다.

## §4. 데미지 공식

### 4-1. 기본 공식

`finalDamage = baseDamage × attackMultiplier × gradeMultiplier × conditionMultiplier × specialMultiplier`

### 4-2. 배율 클램프

최종 배율은 ×0.25\~×4.0 범위로 제한한다. 각성(`awakeningActive`) ×1.25와 옷코츠 주력해방(`burstActive`) ×1.30도 이 클램프 안에 포함한다.

### 4-3. 방어 처리

`isSoulDirect=true`면 effectiveDefense를 0으로 강제한다. `NON\_SORCERER`는 별도 defense 배율을 적용한다.

### 4-4. 변수 무결성

`awakeningActive`, `burstActive`, `healingActive`, `zonePenaltyUntilTick`, `bindingVowDeclaredTick`은 모두 `PlayerData`에 선언되어야 한다(§13-1 참조).

`DamageContext` 필수 필드:

&#x20;   boolean isSoulDirect      // true = 방어 무시, soul damage 로그
    boolean bypassRCT         // true = RCT로 즉시 회복 불가
    UUID attackerUuid
    UUID targetUuid
    String skillId
    float rawDamage
    float finalDamage

## §5. 주력(CE) 시스템

### 5-1. CE 기본

CE는 `ceCurrent`와 `ceMax`로 관리한다. 재생은 `CEManager.regenTick(player)`에서 `CERegenRule`을 참조해 계산한다. `CERegenRule`은 캐릭터, 등급, 전투 상태(`lastCombatTick` 기준), 패시브를 입력으로 받아 틱당 재생량을 반환한다. `CEPool`은 캐릭터별 재생 규칙을 캐싱한다.

### 5-2. CE 소모

스킬 사용 시 서버가 CE를 먼저 예약 차감한다. 검증 실패 시 차감하지 않는다. 영역 전개와 손가락 획득은 즉시 저장 대상이다.

### 5-3. CE 부족

CE 부족 시 스킬은 실패하고 `SkillResultS2CPacket`으로 실패 사유를 전송한다.

## §7. 등급과 성장

### 7-1. 등급별 데미지 배율

|등급|데미지 배율|패시브|
|-|-|-|
|4급|×1.0|없음|
|3급|×1.15|없음|
|2급|×1.30|없음|
|1급|×1.50|없음|
|준특급|×1.65|없음|
|특급|×1.80|캐릭터 고유 패시브 1개|

### 7-2. 등급별 스킬 해금

PvP/PvE 등급 배율은 분리한다. 기본값: `gradePvpScaling=true`.
`unlockedSkills`는 캐릭터 선택 시 현재 등급에 맞게 초기화한다. 등급 기반 해금 조건은 `CharacterCommandService`가 `CharacterRegistry`와 협력하여 처리한다.

> ⚠️ 등급별 구체적인 스킬 해금 목록은 각 캐릭터 확정 시 techniques.json에 `unlockGrade` 필드로 명시한다.

## §9. 반전술식과 상태 이상

### 9-1. 반전술식(RCT)

`healingActive=true`인 동안 CE를 초당 소모하고 HP를 회복한다. `DamageContext.bypassRCT=true`인 영혼 데미지는 RCT로 즉시 복구할 수 없다. `healingActive`는 `PlayerData`에 단일 필드이며, 이타도리(자기회복)와 옷코츠(아군회복)가 모두 이 플래그를 사용한다. 아군 대상 회복 시에는 대상 플레이어의 `PlayerData.healingActive`를 별도로 세팅하지 않고, 옷코츠 서버 로직에서 직접 대상 HP를 회복 처리한다.

### 9-2. 영혼 데미지

`isSoulDirect=true`면 방어를 0으로 처리하고 별도 soul damage 로그를 남긴다.

### 9-3. 상태 이상

정지, 수면, 둔화, 술식 봉인은 서버 tick에서 만료 시간을 검사한다. 각 상태 이상은 `PlayerData.cooldowns` Map에 `"status\_<type>"` 키로 만료 틱을 저장한다.

## §14. 보안과 검증

### 14-1. 입력 검증

CombatPipeline 1단계에서 아래를 서버 측 검증한다:

* 거리: 공격자-대상 간 서버 측 거리 계산
* 시야: 서버 측 ray-cast
* 쿨타임: `data.cooldowns.get(keyId) > currentTick` 여부
* CE: `data.ceCurrent >= skill.ceCost`
* 캐릭터 소유: `data.characterId.equals(expectedCharId)`
* 진영: `TeamManager.canAttack(attacker, target)`

검증 실패 시 `SkillResultS2CPacket(result=FAIL, reason=...)` 전송. 서버는 아무 상태도 변경하지 않는다.

### 14-2. 레이스 컨디션

손가락 드롭, 캐릭터 중복, 처형검 지급, 영역 소유권 변경은 lock 또는 단일 서버 tick 큐로 원자 처리한다. 구현 예시는 §26-4 `FingerSystem` 참조.
